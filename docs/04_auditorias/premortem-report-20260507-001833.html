Premortem: Implementation Plan de Liberacion Segura a Terceros

Premisa: estamos seis meses en el futuro y este plan ya fracaso. Este informe explica como murio, cual es la suposicion mas peligrosa que hoy seguimos dando por hecha y que cambios conviene hacer antes de ejecutar una sola tarea.

Sintesis

La falla mas probable

Que la capa de liberacion quede atrapada en la complejidad reactiva de R/shiny_app.R y termine divergendo de la API y del codigo generado. El riesgo no es un bug puntual: es que cada camino del producto diga una verdad distinta sobre si algo es interno, revisable o liberable.

La falla mas peligrosa

Construir una herramienta que parece estricta y auditable, pero que no demuestra con datasets realistas que sus transformaciones alcanzan para una liberacion defendible. Eso es peor que fallar ruidosamente, porque crea falsa confianza institucional.

La suposicion oculta

Que se puede superponer una capa defendible de decision de liberacion sobre la app y el core actuales sin extraer primero un contrato compartido de estado, evidencia y semantica de salida.

La revision mas importante

Agregar una Fase 0 de contrato comun antes de tocar UI: modelo puro de release state, alertas, evidencia de revision, tipos de artefacto y tests que exijan el mismo veredicto en UI, codigo generado y API.

Razones crudas de fracaso

  • La implementacion colapso bajo complejidad de estado porque demasiada logica de decision quedo dentro de R/shiny_app.R.
  • Las heuristicas generales y las reglas de bloqueo generaron demasiados falsos positivos.
  • Se rompio persistencia JSON, fuzzy matching y continuidad de plantillas.
  • La revision manual y la auditabilidad quedaron superficiales.
  • UI, codigo generado y API quedaron con semanticas contradictorias.
  • Se probaron mas estados y etiquetas que adecuacion real de transformaciones sobre datasets serios.

Deep Dives

1. Complejidad de estado en R/shiny_app.R

Severidad alta Probabilidad alta

El equipo agrego reactividad para estado de liberacion, razones de bloqueo, revisiones, persistencia y fuzzy recovery directamente dentro del servidor. Una misma accion terminaba disparando clasificacion, recalculo de riesgo, recomputo de estado, refresco de persistencia y render de UI. El orden de eventos paso a importar tanto como las reglas mismas.

Cuando intentaron preservar persistencia y fuzzy matching, las revisiones se asociaban a columnas equivocadas o el estado quedaba bloqueado tras arreglos validos. El equipo gasto semanas corrigiendo cadenas de observeEvent() en vez de cerrar un modelo estable.

Supuesto: Shiny reactivity alcanzaba como arquitectura para orquestar politica de liberacion.

  • Cada nueva regla entra como mas reactiveVal() y observeEvent().
  • El mismo caso cambia de estado segun el orden de acciones del usuario.

2. Falsos positivos y fatiga de bloqueo

Severidad alta Probabilidad alta

La politica general conservadora termino siendo demasiado tosca para datasets institucionales corrientes. Patrones nominales, fechas y combinaciones saltaban todos juntos y convertian la app en una fabrica de Bloqueado incluso para flujos rutinarios.

Las plantillas JSON ya no reducian de verdad el esfuerzo de revision, porque pequenos cambios de esquema reabrían alertas y confirmaciones una y otra vez. Los equipos empezaron a ver a ObfuscatoR como una liturgia de cumplimiento, no como una herramienta de trabajo.

Supuesto: Una unica politica general conservadora podia ser defendible sin volverse insoportablemente ruidosa.

  • Mas de la mitad de los datasets piloto quedan bloqueados tras una primera pasada completa.
  • Los usuarios recurrentes siguen resolviendo las mismas alertas pese a usar plantillas.

3. Regresion de persistencia y fuzzy matching

Severidad alta Probabilidad media

La continuidad operativa se trato como una alineacion tardia y no como un contrato central. Cambiaron defaults y semanticas, pero no se cerro temprano una historia de migracion para plantillas ni para el acople con metadatos nuevos de revision.

El resultado fue una nueva version mas lenta para los casos recurrentes: plantillas que reabren como En revision, flags reseteados y sugerencias fuzzy que ya no reconstruyen un flujo continuo. La mejora conceptual se percibio como una degradacion operativa.

Supuesto: Persistencia y fuzzy matching eran una comodidad periferica y no parte del contrato central del producto.

  • Plantillas viejas cargan con estados degradados o incompletos.
  • Un dataset recurrente tarda casi lo mismo que uno nuevo.

4. Auditabilidad superficial

Severidad alta Probabilidad media

La revision manual quedo reducida a metadatos livianos: aprobado, comentario, tratamiento elegido. Eso puede servir para una demo, pero no para sostener una liberacion cuestionada por auditoria, legal o un colega que quiera reconstruir el caso.

Cuando se pidio el rastro de una liberacion, el sistema podia explicar la conclusion, pero no demostrar como se resolvio cada alerta, con que verificacion activa y con que reevaluacion posterior. La defendibilidad se desarmo justo donde mas importaba.

Supuesto: Con algunos campos estructurados y exportacion bloqueada la evidencia resultante seria automaticamente defendible.

  • Los registros de revision no tienen alert IDs, datos verificables ni before/after.
  • Un informe de liberacion no permite reproducir la decision completa.

5. Divergencia entre UI, codigo generado y API

Severidad alta Probabilidad alta

La UI paso a hablar de artefactos internos y liberables, pero el codigo generado y la API siguieron viendose como caminos de transformacion mas permisivos. Un usuario podia encontrar la UI bloqueada y, aun asi, ejecutar un script generado o usar obfuscate_dataset() de forma directa y tratar esa salida como si ya estuviera aprobada.

Sin un veredicto compartido entre los tres caminos, ObfuscatoR termina con tres verdades paralelas. Eso destruye confianza institucional porque nadie sabe que salida gobierna realmente la decision de liberacion.

Supuesto: Al corregir primero la semantica de la UI, los otros caminos quedarían alineados casi por arrastre.

  • Una sesion bloqueada sigue generando codigo ejecutable sin marca explicita de internal-only.
  • No hay tests transversales UI/API/codigo generado con el mismo veredicto esperado.

6. Mucha gobernanza, poca prueba de transformacion real

Severidad alta Probabilidad media

El plan puede llegar a producir una herramienta muy buena para decir Bloqueado, pero insuficiente para demostrar cuando un dataset complejo si se vuelve defendiblemente liberable. Si el esfuerzo de desarrollo y test se va casi todo a estados, heuristicas y reportes, la revision seria va a encontrar una carcasa de gobernanza con un motor poco validado.

Esa es la falla mas peligrosa porque da falsa confianza. No solo frustra al usuario: puede dejar a la organizacion creyendo que tiene un proceso seguro cuando en realidad solo tiene un proceso prolijo.

Supuesto: Estados fuertes, heuristicas y auditabilidad pueden compensar no haber probado a fondo la adecuacion del motor con datasets realistas.

  • Casi todos los tests nuevos son de helpers y transiciones de estado.
  • No hay 2-3 demos credibles que terminen en Liberable con evidencia realista.

Plan revisado

Revision 1

Agregar una Fase 0 de contrato comun: release_state, release_verdict, alert objects, evidencia de revision y tipos de artefacto.

Revision 2

Subir persistencia y fuzzy matching al principio del plan. No dejarlos como limpieza de Fase 4.

Revision 3

Forzar que toda regla nueva nazca en helpers puros con test antes de tocar el servidor Shiny.

Revision 4

Definir fixtures realistas que prueben tanto un caso liberable como uno no liberable sin rediseño.

Revision 5

Endurecer auditabilidad: no hay informe de liberacion sin alert ID, verificacion activa, accion, reevaluacion y before/after.

Revision 6

Agregar una puerta de ruido operativo: medir bloqueos persistentes, revisiones repetidas y tiempo real de reuso con plantillas.

Checklist previo a ejecutar

  • Existe un contrato puro compartido para estado, evidencia, alertas y tipos de artefacto.
  • Hay al menos un test que exige el mismo veredicto de liberacion en UI, codigo generado y API.
  • Hay fixtures realistas para un caso Liberable y otro No liberable sin rediseno.
  • Persistencia JSON y fuzzy matching pasan pruebas de continuidad antes de rearmar el flujo principal de parametros.
  • Una revision manual deja evidencia suficiente para reconstruir toda la decision sin depender de la sesion viva.
